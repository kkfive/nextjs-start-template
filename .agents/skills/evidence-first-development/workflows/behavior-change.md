# Behavior Change Workflow

## 1. 分析与调查

1. 用可观察语言描述目标行为、非目标、用户/调用方和关键不变量。
2. 搜索现有实现、测试、调用方、公共导出、类型/契约和相邻模块；记录直接与运行时消费者。
3. 将正常、错误、边界和不变行为写成 Given / When / Then 或等价验收标准。
4. 按 `references/evidence-matrix.md` 选择最低有效证据，按 `references/impact-and-regression.md` 规划回归范围。

需求歧义会改变产品行为、公共契约或安全边界时，先请求用户决策；不要用测试固化猜测。

## 2. RED

1. 在生产实现未改变的基线上新增或调整目标证据。
2. 运行最聚焦的命令并确认失败。
3. 检查失败是否直接对应某条验收标准；import、环境、fixture、mock 或测试发现失败先修复测试基础设施，不能记为 RED。
4. 如果测试首次即通过，调查行为是否已存在、断言是否过弱、mock 是否绕过真实路径或命令是否跑错；在解释清楚前不进入实现。

## 3. GREEN 与重构

1. 只实现让既定证据通过的最小生产变更。
2. 使用同一目标命令取得 GREEN。
3. 在测试保护下重构，不扩大任务范围。
4. RED 后若需改动验收证据，记录是需求澄清、公共接口判断错误还是测试缺陷；禁止只为通过而放宽断言。

## 4. 回归与验收

按同心圆执行：目标证据 → 所属 workspace → 直接消费者 → `pnpm verify` / `pnpm test:run` → 必要 build、集成或 E2E。

高风险变更安排独立验收。最终按 `references/acceptance-and-reporting.md` 报告需求映射、RED/GREEN、回归、验收与残余风险；不要声称零 bug。
