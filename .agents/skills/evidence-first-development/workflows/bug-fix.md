# Bug Fix Workflow

1. 从缺陷报告提取期望行为、实际行为、复现条件、影响范围和明确非目标。
2. 沿真实调用链复现，不先修改生产代码。优先把复现固化为最接近缺陷边界的自动化回归测试。
3. 运行复现证据并确认：
   - 旧实现失败；
   - 失败现象与报告一致；
   - 失败不是环境、导入、fixture 或 mock 配置问题。
4. 无法自动化时，记录可重复的命令、浏览器/API 步骤、输入、环境和实际输出，作为等价 RED。
5. 实施最小修复，以同一证据确认 GREEN；不得删除、跳过或弱化复现断言。
6. 检查同一根因的相邻路径、错误路径和边界条件，补充有判别力的回归证据。
7. 按 `references/impact-and-regression.md` 扩大验证，并由独立验收者根据原始缺陷重新执行关键复现。

若无法稳定复现，不得把猜测性改动表述为已修复；应报告调查结果和剩余假设。
