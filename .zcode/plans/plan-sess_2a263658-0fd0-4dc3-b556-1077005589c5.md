# Phase 1-3 完整实施计划：monorepo 落地

## 总体策略

连续执行 Phase 1（搬迁 + 骨架）→ Phase 2（提取共享包）→ Phase 3（示例 apps），中间不暂停审查，最终统一 review。每个 Phase 完成后跑 `pnpm install` + `turbo build/lint/typecheck/test` 验证可用，再进入下一个 Phase。

文档遵循"最简化"原则：主要面向用户理解项目，不堆细节（细节从代码和 `.agents/` 规范获取）。

## 关键实施决策（我按文档+探索结果自行确定）

1. **git mv 保留历史**——搬迁用 `git mv` 而非 cp+rm
2. **@esdora/date 删除**（零引用死依赖）
3. **废弃的自定义 `button/` 目录删除**（仅自测试引用，与实际用的 `button.tsx` 冲突）
4. **domain/_shared/ 的 types 进 contracts、utils 进 packages/utils**（无任何引用，安全提取）
5. **BusinessError 进 http-client**（有 throw/instanceof 行为，被 domain 和 app 共用）
6. **响应 envelope 类型进 contracts**（HttpResponseSuccess/Error 是 API 数据契约）
7. **react-query 系列留 apps/client**（hooks 是 app 适配层，文档明确）
8. **antd 留 apps/client**（仅 2 处用，在 common/，文档明确 app 自治）
9. **文档最简化**：删除 architecture.md/conventions 重复内容，重写 readme 为面向用户的简入口
10. **Phase 1 的 domain/ 整体搬迁，Phase 2 才拆分**（避免 Phase 1 同时搬+拆的复杂性）

## 工作量与风险

- **Phase 1**：最大批次，约 60+ 文件移动 + 10+ 新配置文件。风险点是 git mv 后的 import 路径（别名 `@/*`、`@domain/*` 在 apps/client 内仍成立，无需改 import）。
- **Phase 2**：提取 5 包 + 改造 client 适配层。风险点是 domain-core 的 import 重写（`@/lib/request` → `@kkfive/http-client`）。
- **Phase 3**：新建 2 app，独立性强，风险低。

全程不触碰业务逻辑（只是搬家+改 import），源码语义不变。最终你做统一 review 时，可以重点看：包依赖边界、tsconfig project references、turbo 任务图、文档简化是否合理。
